# 设备用户画像

日期：2026-10-19。本文记录本轮本地 Web 修改；未推送、部署或重打包，不改变独立 MCP 的记忆指导，也不重开 W 队列。

## 用户行为

1. 首次打开网站时，在当前浏览器的网站存储中建立随机设备标识，不需要注册、账号或密码。
2. 规划结果或后续对话修改结果展示完成后，页面另发后台请求，让 DS 根据本轮用户原话、待回答澄清的原始需求及明确填写的出行条件整理画像。不会等待画像完成才展示行程，也不把已完成的旧对话反复作为新证据。
3. 编辑器中的实际行程修改，包括酒店选择，在提交完成后也会触发更新；仅整理为本次旅行信息。撤销、采用既有候选、收藏恢复不重复学习，示例、澄清中、失败和取消不更新。
4. 后续规划参考已保存的长期画像。本次明确要求、表单和当前采用行程优先；历史地点不会自动成为必去点，家庭成员不会自动成为本次同行。
5. 打开“偏好设置 → 用户画像”，可查看分类、内容、长期/本次旅行、来源、更新时间及原话依据，补充、纠正或删除条目，也可确认清空。后台更新失败保留原内容，并提供重试入口；失败不撤回已完成的行程。

清空只作用于画像，不清除手动保存偏好、行程收藏或设备标识。

## 内容与更新规则

分类由 DS 根据实际输入归纳，可以包含兴趣、家庭信息、特殊需求、日常作息、饮食、体力、交通、住宿、预算与旅行节奏等。家庭关系、年龄、健康或收入不能根据措辞、单次同行、选过的地点猜测。

长期事实与本次旅行分开保存。用户明确的一贯习惯、长期喜好或家庭事实才能归入长期；“这次带父母”“今天晚起”“此次预算”属于本次旅行，未来新规划不会把这些条目作为默认画像。一次手动换酒店或改时间也不能变成长久偏好。

新增、修改和移除须有本轮用户来源中的连续原文证据；不会把助手建议、生成路线或系统默认值当成用户自述。DS 合并相关信息，保留无关旧条目，纠正沿用原条目 ID；人工确认项只有明确纠正时才能被 DS 改动。只保存有界条目及原话片段，不保存完整对话。最多 40 项，分类 40 字、标题 60 字、内容 320 字、依据 500 字；可识别凭据会被清理，当前 Key 不进入画像。

每次后台更新使用一个独立 DS 请求、服务端 25 秒超时，不重试模型；它不占规划的模型/工具/时间预算。页面内串行处理更新，每次读取最新画像。人工修改、删除、清空或另一标签页更新后，旧请求结果会被丢弃，防止覆盖新内容；删除的信息不会因无关后续请求重新读取旧聊天而恢复。用户以后再次主动提供相关信息时，仍可形成新条目。

## 设备与资源边界

| 场景 | 行为 |
| --- | --- |
| 同一浏览器、同一网站 origin 的多个标签页 | 共用设备标识、画像和保存偏好，通过 storage 事件同步 |
| 不同设备、不同浏览器或浏览器配置文件 | 各自独立，不需要账号 |
| 相同设备访问不同域名、协议或端口 | 浏览器视为不同 origin，资料不共享；本地站和线上站也是独立的 |
| 多个人共用相同浏览器配置文件 | 共用同一份资料，无法自动区分实际使用者 |
| 无痕模式、清理网站数据或浏览器回收数据 | 可能丢失设备标识及资料，不提供云恢复 |
| 网站存储被禁用或写入失败 | 降级为当前页面内存，设置会提示；刷新可能丢失 |

随机设备标识保存在 `citywalk.device.id.v1`；画像和手动保存偏好位于 `citywalk.device.<设备标识>.resources.v1`。这是一种浏览器本地身份，不是物理设备指纹或服务器账户。既有行程收藏继续使用当前 origin 的 IndexedDB；本轮未迁移收藏库。Key 继续使用原标签页 sessionStorage，不进入画像资源。

服务端不持久保存画像。规划时只发送所需长期摘要，后台整理时发送已有画像和本轮用户依据。公开路书、JSON、分享和收藏备份白名单不附带整份画像或保存偏好；行程自身的同行、住宿、预订和自由文字仍遵循既有导出规则。

后台请求队列与待处理输入只留页面内存；关闭或刷新页面可能中断更新，失败重试也不能跨刷新恢复。画像不承诺云同步或永久保存；多个标签页同时手动写入同一资源时以后写为准，没有数据库事务锁。

## 实现入口

| 文件 | 职责 |
| --- | --- |
| `public/profile-schema.mjs` | 前后端共享条目规范化、字段上限、凭据清理、长期摘要 |
| `lib/user-profile.js`、`server.js` | `POST /api/profile/update`，独立 DS 调用、证据校验与合并，无服务器画像库 |
| `public/device-profile.mjs` | 本地设备资源、持久化与跨标签同步、后台队列、过期响应保护、失败重试 |
| `public/profile-input.mjs` | 仅从当前用户请求/待澄清需求/明确条件及实际手动差异提取依据 |
| `public/profile-view.mjs`、`public/profile.css`、`public/index.html` | 设置入口、展示与人工管理 |
| `public/app.js`、`public/editor-view.mjs`、`public/conversation-view.mjs` | 结果展示后入队、编辑与撤销区分、保存偏好同步 |
| `lib/conversation.js`、`lib/conversation-planner.js`、`lib/agent-decision.js`、`server.js` | 把长期画像接入规划，并保持当前明确需求优先 |

接口请求为 `{ apiKey?, profile, input: { kind, prompt?, messages?, context?, changes? } }`，`kind` 为 `planning`、`edit` 或 `manual`，成功返回 `{ profile }`。前端只提供当前轮所需的用户来源，不发助手内容或已完成的旧聊天。格式错误返回 400，Key 鉴权失败 401，缺 Key 503，其余模型失败 502；错误不含供应商响应原文或凭据。

## 同日设置页排布调整

用户反馈设置页出现大块留白、画像入口重复。原因是四张卡共用双列网格，AI 连接卡的高度把下一行出行条件整体推低。

本次将页面改为左右独立纵向排布：左列是画像与本次出行条件，右列是 AI 连接与手动偏好；1000px 以下按画像、出行条件、AI 连接、手动偏好的顺序单列。去掉重复外层标题及画像内层边框，画像默认展开且可折叠，桌面长列表内部滚动、手机随页面展开。出行条件六个字段改为三行双列，右侧偏好输入按字段纵向对齐。保留原挂载点、字段 ID 和跨页面条件校验关联；修正原交通下拉中步行项的错误 option 标签，七个选项完整。

修改 `public/index.html`、`public/workspace.css` 和 `public/profile-view.mjs`。本次单独运行页面结构、画像管理和出行条件校验共 8 项测试，全部通过；画像视图语法通过；首页、样式及视图模块本地 HTTP 200 且内容与当前文件一致。未追加浏览器/Playwright、模型或供应商验证，未重启、推送、部署或重打包。现有本地服务直接提供新静态文件，刷新设置页即可加载。
