## 一、核心方向

**以 City Walk 为比赛切入点，利用 AI 的世界知识选点和规划线路，通过真实数据与约束校验确保方案落地，再用地图支持实际出行；长期扩展为能持续理解用户、反思调整规划并生成完整路书的旅行规划智能体。**

老师强调，需要先想清楚产品当前和未来分别能为用户提供什么价值，再决定比赛期间增加哪些功能。

## 二、产品可优化的点

### 1. 把行程做细，让用户能够照着走

- **老师指出的问题**：普通大模型通常只给出“上午去哪些地方、下午去哪些地方”，缺少具体的时间安排和游玩动线。
- **优化方向**：结合景点建议游玩时长、地点之间的交通耗时，展示每个地点的到达时间、停留时间，以及到下一站的安排。
- **用户价值**：用户能够提前理解一天的节奏，拿到行程后更容易实际出行。
- **原文时间**：05:01—07:40、10:05—12:26。
- **后续电话补充**：按用户选择的交通方式，清楚呈现景点之间的耗时以及每天的交通总耗时，帮助用户判断一天的出行负担。时间：00:00—01:08。

### 2. 加强地图与路线展示

- **老师指出的问题**：用户拿到文字行程后，仍然需要自己查地点、查地图、研究怎么走。
- **优化方向**：在地图上直观展示地点位置、访问顺序、具体路径和分段交通耗时，并提供地点特色等信息。
- **后续方向**：出行时连接高德地图开启导航，把规划与实际出行衔接起来。
- **注意**：地图路线展示与实际导航是不同能力；尚未实现的导航应在路演中作为未来规划介绍。
- **原文时间**：01:28—01:56、07:40—08:03、10:21—12:26、14:08—15:40。

### 3. 让行程可以调整，并保证调整后仍然合理

- **老师指出的问题**：AI 第一版方案不一定完全符合用户要求，一份不能修改的固定行程难以适应实际需求。
- **优化方向**：
  - 提供主选点和备选点，支持“换一个”。
  - 用户觉得太累时，可以删除部分地点。
  - 用户发现新的有趣地点时，可以尝试加入行程。
  - 允许用户补充偏好，逐步生成更合适的路线。
- **关键约束**：替换、增删之后，需要重新检查路线和时间安排，避免出现绕路过远或行程走不完的问题。
- **原文时间**：03:00—04:19、14:41—15:11。

### 4. 从 City Walk 扩展到城市一日游

- **老师的建议**：首次讨论提出可评估比赛期间扩展到城市内一日游；后续电话将城市一日游和多交通方式纳入未来能力介绍。因此，更新后的范围建议是先保证 City Walk 核心演示完整，再按实际余力取舍扩展。
- **新增考虑**：景点停留时间、开放时间，以及步行、骑行、打车、自驾等出行方式对地点选择和交通耗时的影响。
- **扩展顺序**：先把单一场景做好，再考虑更多交通方式和更大区域；跨城规划复杂度更高，适合作为后续方向。
- **注意**：老师提出的是可评估的扩展方向，并未要求比赛前完成全部出行方式。
- **原文时间**：04:24—08:23、11:26—12:59、15:56—16:22。
- **后续电话时间**：00:00—01:08。

### 5. 增加行程导出

- **老师的建议**：编辑完成后，应当能够生成可打印的行程单；老师认为这一功能可能较快补充。
- **用户价值**：方便用户离线参考或打印使用。
- **后续方向**：产品成熟后，可以收藏行程，在出行时重新打开使用。
- **原文时间**：08:28—08:58。

### 6. 增加行程分享

- **老师的建议**：为生成的行程提供分享链接，老师自己的 Demo 使用了分享短链接。
- **用户价值**：同行者打开链接即可查看同一份规划，方便出行前沟通。
- **注意**：对话未明确链接权限、有效期或共同编辑等具体机制。
- **原文时间**：08:58—09:46。

### 7. 从行前规划延伸到旅行途中

- **老师的设想**：产品未来可以成为一份能够动态使用的旅行指南。
- **优化方向**：旅行途中结合地图发现周边有趣地点，展示距离及前往所需时间，并支持调整后续安排。
- **用户价值**：让产品在生成行程之后仍然有使用价值。
- **原文时间**：10:38—11:26、15:11—15:40。

### 8. 从路线骨架扩展为完整、个性化的路书

- **后续电话新增观点**：路线只解决“怎么走”，是行程的骨架；真正出行还需要相关准备、注意事项和配套方案。
- **优化方向**：在已生成的路线和用户需求基础上，让 AI 补充有针对性的出行提示（Tips），形成完整路书。老师展示的思路是生成 HTML 格式路书。
- **老师的例子**：用户要去苏州环湖骑行三天，Agent 先询问自带自行车还是租车；在知道用户需要租车后，路书进一步补充租车地点、租车方案及适合的自行车类型等信息。
- **用户价值**：从“知道去哪里”延伸到“知道出发前要准备什么、到当地如何执行”，减少用户自己补查信息的工作。
- **与行程导出的关系**：导出解决已有行程如何带走；完整路书还需要补充内容，两者可以结合，但不是同一个功能。
- **落地参考（整理建议）**：涉及具体租车点、营业情况、天气或自行车乘车规则时，应核实对应地点、日期和交通运营方的信息，不能把模型举例直接当作有效事实。
- **范围判断**：老师将此项作为未来方向，没有要求比赛前做完；若已有相关能力，可以挑选一个场景展示。
- **后续电话时间**：02:42—05:21。

## 三、技术实现可优化的方向

### 1. 用真实 POI 和地图数据校验模型结果

- 对大模型提出的地点进行真实 POI 匹配，确认地点存在，并补充坐标、图片等信息。
- 从地图服务获取地点之间的路线和交通信息，使规划能够落到地图上。
- 真实地点匹配与行程可行性需要分别验证：地点存在，并不自动意味着当天开放或整条路线合理。
- **原文时间**：00:58—02:16、16:22—16:54。

### 2. 保留硬约束校验，长期逐步减少算法对选点的干预

- **首次讨论的实践**：纳入开放时间、闭馆日期、建议游玩时长和交通耗时，通过剔除、调整与路线重排提高行程可行性。老师提到的重排算法转写为“top TW”，具体名称和实现需结合仓库确认。
- **后续电话的进一步判断**：为每个不合理场景不断增加算法规则，难以穷尽所有情况；未来可以更多借助 Agent 的世界知识和推理能力判断、调整路线。
- **老师设想的职责分配**：选点和综合规划判断逐步交给 Agent；算法与数据校验保留地点是否存在、当天是否闭馆等硬指标的检查。
- **与当前项目的关系**：这是老师对未来架构的设想，不等于要求比赛前拆除已有算法。应先确保现有演示稳定，再评估逐步调整。
- **原文时间**：01:40—02:44、05:16—06:19；**后续电话时间**：01:08—03:28。

### 3. 比较两种规划流程，避免标签检索丢失意图

| 流程 | 对话中的说明 | 需要关注的问题 |
| --- | --- | --- |
| 理解需求 → 检索 POI → 基于检索结果生成路线 | 团队描述的思路，也是老师早期做过的版本 | POI 标签可能无法表达完整需求，尤其骑行体验往往与整条线路有关 |
| 理解需求 → 大模型提出路线 → 匹配 POI 并校验 | 老师在骑行场景遇到问题后尝试的版本 | 借助模型对场景的整体理解，同时仍要校验地点和路线 |

首次讨论中，老师没有系统比较两种方式。后续电话进一步强调，AI 利用世界知识规划线路和选点是项目的技术亮点，并提出未来选点应更多忠实于 Agent、减少算法干预的方向。这表明了老师的方向偏好，但仍不构成两种流程的效果评测，也不等于比赛前必须重构当前方案。

**原文时间**：16:54—19:38；**后续电话时间**：00:00—00:30、02:42—03:28。

## 四、长期方向：旅行规划智能体

### 1. 支持多轮对话

- 第一版行程生成后，用户可以继续说“老人太累了，希望轻松一点”，系统应结合前文调整方案。
- 信息不足时，先澄清同行人员、出发时间、交通方式等，再进行规划。
- 转写中的“多人对话”，结合上下文应理解为“多轮对话”。
- **原文时间**：20:46—21:49、24:02—25:01。
- **后续电话明确的范围**：用户每一轮只需补充部分信息，系统结合已有上下文继续完善规划；但老师明确不建议在本次比赛剩余时间内赶做多轮对话，应先把它纳入产品蓝图。时间：05:45—07:32。

### 2. 建立用户画像与历史偏好记忆

- 团队提出用户画像，老师认可这一方向，并进一步讨论历史偏好和上下文的作用。
- 在新需求中结合用户已提供的信息，减少重复描述，让规划逐步贴合个人需求。
- 画像需要结合本次出行重新确认。例如，上一次带坐轮椅的父母出行，不代表这一次亲子出行也沿用相同条件。
- **原文时间**：21:34—21:49、23:13—26:33。
- **后续电话补充**：判断路线时还可结合本次是否带小孩、是否有使用轮椅的父母、出行当天天气等上下文。天气属于需要按出行日期获取的动态信息。时间：02:14—02:42。

### 3. 把规划能力封装为 Agent 可调用的工具

- 老师将自己的应用接口封装为 MCP，并接入 WorkBuddy，利用其需求理解、上下文和记忆能力。
- 同时通过 MCP App 展示地图和详细行程，让工具调用结果具有可交互界面。
- 后续电话明确：网页对话框只是交互界面，后端可以接入 Agent 框架；用户仍然在网页或 App 中提出需求，上方展示地图、路线和路书，背后由 Agent 调用工具完成服务。
- MCP 接入外部助手是老师已经尝试的路径；在自己的 Web 应用后端运行 Agent 也是可行方向，两者不必绑定。
- 老师提到可以利用现有 Agent 框架搭建，但转写中的框架名称不清楚，不据此指定技术选型；本次比赛以未来架构说明为主。
- **原文时间**：22:10—23:13、25:01—26:57；**后续电话时间**：05:21—07:32。

### 4. 引入生成后的审查与迭代

- 规划器生成一版行程后，Agent 再结合常识判断路线是否合理。
- 如果发现问题，重新调用规划器生成多个版本，再进行比较。
- 老师举例：武汉行程出现一天内往返跨长江的问题，Agent 识别后重新规划，比较了约 3—4 个版本。
- 对话展示了这种方式的潜力，但未提供系统评测，也未证明 Agent 可以替代真实数据与约束校验。
- 后续电话强调，Agent 应在了解用户的情况下，主动多轮反思和调用工具，使规划更合理；其作用包括结合上下文调整路线，以及在路线基础上补充完整路书。
- **原文时间**：26:57—28:55；**后续电话时间**：01:08—05:21。

## 五、比赛展示可优化的方向

### 1. 用用户故事组织演示

老师建议以自己作为典型用户，围绕实际使用过程展开：

1. **用户是谁**：喜欢步行探索陌生城市、希望深入感受城市的旅行者。
2. **遇到什么问题**：普通 AI 给出文字建议，但用户仍需自己查地点、路线和交通信息。
3. **产品如何解决**：在地图中展示具体地点、动线和时间安排，并允许继续调整偏好。
4. **未来如何延伸**：连接导航、发现周边地点，扩展到骑行、徒步、自驾等场景。

## 六、建议的推进顺序

> 以下是依据老师建议整理的优先级，供团队取舍。P0 表示优先保证核心演示成立；P1 表示有时间再增加；P2 表示后续探索，不是会议承诺。

| 优先级 | 优化项 | 建议目标或验收参考 |
| --- | --- | --- |
| P0 | 明确核心价值与路演故事 | 围绕 AI 选点规划、真实数据校验落地、地图辅助出行三个亮点，用具体案例讲清用户价值 |
| P0 | 真实地点与地图路线 | 示例行程中的地点能匹配真实 POI，访问顺序和路径展示清楚 |
| P0 | 具体时间安排 | 示例行程展示交通耗时、建议停留时间及全天安排，并检查关键开放时间 |
| P0（表达准备） | 未来蓝图与答辩 | 讲清城市一日游、多交通方式、Web 背后的 Agent 和完整路书，区分现有能力与后续设想 |
| P1 | 行程导出 | 可导出或打印一份完整、可读的行程单 |
| P1 | 备选点与替换 | 至少支持一种调整操作，并重新检查路线与时间 |
| P1 | 分享链接 | 同行者可通过链接查看规划结果 |
| P2 | 城市一日游扩展 | 后续电话将其列为未来能力；本次若有余力，可再评估是否做最小场景扩展 |
| P2 | 多交通方式与更多区域 | 逐步支持骑行、自驾、多日及跨城场景 |
